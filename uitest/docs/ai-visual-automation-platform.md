# AI 视觉多端自动化回归平台方案

## 1. 建设目标

建设一个面向招聘业务的 AI 视觉自动化回归平台，让测试、产品、业务、研发都能用自然语言编写回归用例，并在 PC Web、微信小程序、App 等多端执行。

核心目标：

- 自然语言写用例，降低自动化门槛。
- 通过 AI 视觉识别理解页面状态，通过 AI 指令解析理解用户意图。
- 支持 `@AI填表`、`@AI对话` 等平台指令。
- 支持 PC Web、微信小程序、App、接口自动化统一管理。
- 小程序和 App 执行前做真机检测，避免设备问题误判为用例失败。
- 逐步支持页面、AI 视觉、AI 语义、接口、数据库、消息/日志多层断言。

首期边界：

- 只支持结构化自然语言 Case，不做完全自由文本解析。
- 只支持 `@AI填表`、`@AI对话` 两类 AI 指令。
- 优先跑通 PC Web + 微信小程序，App 端作为后续扩展。
- 优先选择 1 到 2 条招聘核心链路，接口校验只接入关键查询接口。

## 2. 平台定位

本平台不是单纯依赖传统元素定位的自动化平台，而是以 AI 视觉识别为主、传统定位和接口校验为辅的多端自动化回归平台。

| 对比项 | 传统元素定位方案 | AI 视觉自动化方案 |
|---|---|---|
| 用例编写 | 编写代码，维护 CSS、XPath、控件 ID | 用自然语言描述步骤和断言 |
| 元素识别 | 依赖 DOM、控件树、Accessibility ID | 依赖截图、OCR、视觉模型、字段语义 |
| 测试数据 | 手工准备字段数据 | `@AI填表` 根据业务意图自动填写 |
| 会话场景 | 逐轮编写输入内容 | `@AI对话` 自动生成多轮输入 |
| 多端支持 | Web、App、小程序工具割裂 | 统一执行适配层 |
| 稳定性兜底 | 传统定位为主 | 传统定位、接口、数据库作为兜底校验 |

落地结论：

- 主链路：自然语言用例 + AI 指令解析 + AI 视觉执行。
- 亮点能力：智能填表、会话式用例、多层断言、真机检测。
- 接口自动化用于数据准备和结果校验，不替代 AI 视觉自动化回归。

## 3. 总体架构

```text
用户自然语言用例 / AI 指令
  ├─ 普通步骤：点击、输入、断言、等待
  └─ AI 指令：@AI填表、@AI对话
  ↓
Case 解析与执行计划生成
  ├─ 可执行步骤
  ├─ AI 填表参数
  ├─ AI 会话参数
  └─ 断言规则
  ↓
执行前检查
  ├─ 环境变量检查
  ├─ 账号/测试数据检查
  └─ 小程序 / App 真机设备检测
  ↓
任务调度与资源锁
  ├─ Web 任务可并发
  └─ 小程序 / App 真机任务按设备串行
  ↓
多端执行适配器
  ├─ PC Web 执行器：Playwright + Midscene.js
  ├─ 小程序/App 执行器：Airtest / Appium + AI 视觉识别
  ├─ 接口执行器
  └─ MCP 工具服务适配（预留）
  ↓
执行与校验
  ├─ 执行动作：页面操作、智能填表、会话输入输出
  ├─ 页面校验：文案、按钮、列表、弹窗、页面状态
  ├─ AI 校验：截图识别、页面状态判断、会话回复语义判断
  └─ 后端校验：接口、数据库、消息日志（逐步完善）
  ↓
报告与分析
  └─ 截图、视频、日志、字段填充明细、会话明细、失败分析
```

MCP 定位：首期优先平台内置适配器，保证 PC Web 和小程序 POC 快速跑通；同时预留 MCP 工具服务接口，后续可将 Playwright、ADB、Airtest/Appium、接口请求封装为 MCP 工具。

## 5. 用例与 AI 指令

首期建议优先支持结构化自然语言，后续再支持纯自然语言自动拆解。

Case 管理重点维护：业务流程、执行端、结构化步骤、AI 指令、断言规则、测试数据、标签、版本和执行历史。用户维护业务意图，平台生成执行计划。

### 5.1 结构化自然语言

```yaml
name: 登录后查看候选人列表
platform: web
env: test
steps:
  - 打开招聘管理后台
  - 输入测试账号和密码
  - 点击“登录”
  - 进入候选人管理页面
  - 断言页面出现“候选人列表”
```

### 5.2 AI 智能填表

适用于发布职位、创建候选人、录入面试反馈等复杂表单场景。Case 的核心不是脚本，而是业务意图、AI 填充要求和断言目标。

```yaml
name: 发布招聘岗位
platforms: [web, miniapp]
business: 职位管理
steps:
  - 打开职位管理页面
  - 点击发布职位
  - @AI填表: 发布一个上海高级 Java 开发职位，薪资合理，描述完整
  - 点击发布
assertions:
  - 页面出现发布成功
  - 职位列表能看到新职位
  - 接口查询职位状态为已发布
```

约束：

- 首期只允许在测试环境使用。
- 高风险字段需要人工确认或规则限制。
- 敏感字段支持黑名单，例如手机号、身份证、银行卡、生产账号。
- 报告中记录字段填充明细和失败原因。

### 5.3 AI 会话式用例

适用于招聘助手、简历问答、职位推荐、候选人沟通等多轮交互场景。

```yaml
name: 招聘助手多轮会话
platform: web
steps:
  - 打开招聘助手页面
  - @AI对话:
      目标: 咨询高级 Java 开发岗位要求，并确认招聘助手是否给出岗位匹配建议
      最大轮次: 5
      终止条件: 招聘助手给出岗位要求说明或候选人匹配建议
      断言: 回复内容与岗位要求或候选人匹配相关，且没有答非所问、空回复、异常报错
```

约束：

- 必须配置最大轮次，防止无限对话。
- 必须配置终止条件或断言目标。
- 平台记录每轮输入、输出、截图、模型判断和停止原因。

## 6. 多层断言策略

AI 视觉自动化不能只依赖页面提示，应按场景组合断言。

| 断言方式 | 适用场景 | 示例 |
|---|---|---|
| 页面断言 | 用户可见结果 | 页面出现“发布成功”、职位列表新增一条职位 |
| AI 视觉断言 | 页面状态、弹窗、按钮、布局 | 当前页面进入职位详情页，关键按钮可见 |
| AI 语义断言 | 会话回复、长文本提示 | 招聘助手回复围绕岗位要求，且给出匹配建议 |
| 接口断言 | 后端业务状态 | 查询职位详情接口，状态为“已发布” |
| 数据库断言 | 核心数据落库 | 职位表存在当前用户发布的高级 Java 职位 |
| 消息/日志断言 | 异步任务、通知、回调 | 检查 MQ 消息、任务日志、回调日志是否成功 |

推荐组合：

- 发布职位/创建候选人：页面断言 + 接口断言；核心字段再加数据库断言。
- 会话类场景：AI 语义断言 + 异常断言；必要时补页面断言。
- 小程序/App 场景：AI 视觉断言 + 接口断言，减少纯页面判断的不确定性。
- 异步流程：页面断言 + 消息/日志断言，必要时轮询接口状态。

后端校验先按预留能力逐步完善：平台需要维护测试环境、鉴权信息、接口/数据库/日志查询配置；`@AI填表` 生成的字段需要沉淀为 `case_data`，供接口、数据库、消息日志断言引用。

## 7. 多端执行方案

| 端 | 推荐方案 | 重点 |
|---|---|---|
| PC Web | Playwright + Midscene.js | 浏览器控制、AI 视觉识别、截图、视频、Trace。 |
| 微信小程序 | 真机 + AI 视觉识别 + Airtest/Appium | 真机启动、截图、点击输入、页面断言。 |
| App | Airtest/Appium + AI 视觉识别 | 设备连接、安装包管理、点击输入、截图。 |
| 接口 | 自研轻量执行器或集成 Newman/pytest/Karate | 数据准备、状态校验、后置断言。 |

## 8. 真机设备检测

小程序和 App 执行前必须先检测设备，检测失败时阻断任务并给出修复提示。

执行策略：同一台真机同一时间只允许一个任务占用，其他任务进入队列等待；任务结束后释放设备锁。

队列策略：任务按提交顺序排队，执行中不可抢占；任务超时、失败或取消后必须释放设备锁，避免真机资源被长期占用。

| 检测项 | 说明 |
|---|---|
| 开发者模式 | 检查手机是否开启开发者模式。 |
| USB 调试 | 检查 USB 调试是否开启。 |
| 设备连接 | 执行 `adb devices`，确认设备序列号和连接状态。 |
| 设备授权 | 检查是否已允许当前电脑调试。 |
| 截图能力 | 验证是否可以拉取手机截图。 |
| 点击输入 | 验证是否可以执行点击和输入操作。 |
| 应用状态 | 检查微信或被测 App 是否已安装、可启动。 |
| 屏幕状态 | 检查是否亮屏、未锁屏、无系统弹窗遮挡。 |

## 9. 候选开源框架

| 工具 | 适用端 | 作用 | 风险 |
|---|---|---|---|
| Midscene.js | PC Web | AI 视觉自动化 | 复杂业务稳定性需验证 |
| Playwright | PC Web | 浏览器自动化底座 | 本身不是 AI 视觉框架 |
| Airtest | App、小程序 | 图像识别和移动端自动化 | 脚本维护仍需规范 |
| Appium | App | 移动端自动化底座 | 环境搭建和稳定性成本较高 |
| UI-TARS | 桌面、Web、移动 GUI | 通用 GUI Agent | 更偏模型/Agent，不是测试平台 |
| MobileAgent | App | 移动端视觉 Agent | 工程化接入成本需评估 |
| Allure | 全端 | 测试报告 | 分析能力有限 |
| ReportPortal | 全端 | 集中化测试报告分析 | 部署和维护成本较高 |

## 10. 平台优劣势

| 维度 | 优势 | 风险或代价 | 应对方式 |
|---|---|---|---|
| 使用门槛 | 自然语言写用例，非自动化人员也能参与。 | 描述不规范时 AI 理解不稳定。 | 首期采用结构化模板。 |
| 多端覆盖 | PC Web、小程序、App 统一管理。 | 小程序和 App 链路更复杂。 | 首期优先打通 PC Web + 小程序。 |
| 智能能力 | 支持智能填表、会话式用例、多层断言。 | AI 结论可能不完全准确。 | 保留截图、接口、数据库、日志等证据。 |
| 执行成本 | 优先覆盖高频、重复、路径明确的招聘回归场景。 | 截图、视频、模型调用会消耗资源。 | 控制截图频率和模型调用策略。 |
| 扩展性 | 可预留 MCP 工具服务适配。 | 需要治理权限、超时、日志回传。 | 首期内置适配，后续逐步 MCP 化。 |
| 稳定性 | AI 视觉能降低元素定位维护成本。 | 可能出现误识别、页面加载波动、弹窗遮挡。 | 设置置信度阈值、失败重试、传统定位兜底、识别失败不盲点。 |

## 11. 平台建设规划

建设顺序建议按“先跑通 AI 视觉回归，再补齐平台能力”的方式推进。

| 阶段 | 建设重点 | 目标 |
|---|---|---|
| P1 | AI 视觉自动化回归 | 跑通 PC Web + 微信小程序核心招聘流程，验证 AI 视觉识别、点击、输入、断言稳定性。 |
| P2 | Case 管理 | 支持自然语言用例、结构化步骤、标签分组、版本记录、用例评审。 |
| P3 | Case 执行 | 支持任务创建、排队执行、设备锁、真机检测、执行日志、截图、报告、失败分析。 |
| P4 | 用例生成 | 支持基于招聘业务场景生成用例，例如职位发布、候选人创建、简历筛选、面试邀约。 |
| P5 | 接口自动化 | 支持接口用例生成、数据准备、状态校验、多层断言，作为 UI 回归的稳定兜底。 |
| P6 | 平台化管理 | 补齐项目、环境、账号、设备、权限、通知、CI/CD、质量看板等管理能力。 |

首期最小闭环：

```text
自然语言用例
  → AI 指令解析
  → 执行前检查
  → AI 视觉识别与执行
  → 智能填表 / 会话输入（按需）
  → 多层断言
  → 截图、日志、报告
  → 失败分析
```

首期重点验证：AI 视觉自动化回归在招聘核心流程中是否稳定可用，Case 是否易维护，是否支持 PC Web 和微信小程序多端复用。

首期验收标准：

- 能在平台创建结构化自然语言 Case，并执行 PC Web + 微信小程序核心链路。
- `@AI填表` 能完成招聘岗位发布类表单，报告记录字段填充明细。
- 执行过程保留截图、日志、失败原因，失败时不盲目继续点击。
- 真机任务支持排队、设备锁、超时释放和失败释放。
- 至少接入一个关键查询接口作为后端校验预留验证。
